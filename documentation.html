Documentation

Everything you need to install Open4D, understand its data model, and start working with time-varying 4D geometry.

💡

Open4D is under active development. APIs in open4d/ are the stable public surface; modules evolve independently. For the latest state of the code, see the GitHub repository.

Introduction

Open4D is an open, research-driven platform for the representation, compression, processing, evaluation, and streaming of time-varying 4D geometry data. It serves as shared infrastructure for application domains such as XR systems, robotics, teleoperation, digital twins, and autonomous systems, where geometry evolves over time and must be processed under tight latency, bandwidth, and accuracy constraints.

The platform is organized into five layers:

  • Core (open4d/) — canonical 4D data models, IO, metrics
  • Modules — research algorithms (e.g., TVMC, ARAP-based tracking)
  • Benchmarks — paper-reproducible evaluation code, baselines, configs, and scripts
  • Apps — end-to-end pipelines and demos
  • Bindings (cpp/, python/) — performance-critical and research-friendly APIs

Installation

Requirements

  • Python 3.10 through 3.13 for the current package
  • Git (with submodule support, for the N4MC and TSMC compression modules)
  • Unity 2022 LTS or later (only for the XR decoder plugin)

Development install

shell
git clone https://github.com/open4dfoundation/Open4D.git
cd Open4D
pip install -e .

With compression submodules

N4MC and TSMC are integrated as git submodules. To fetch them along with the core:

shell
git clone --recurse-submodules https://github.com/open4dfoundation/Open4D.git

# or, in an existing clone
git submodule update --init --recursive

Quickstart

The scripts in this original quickstart describe the legacy players. Use the current sequence API below for new programs.

The examples/ directory contains minimal, runnable scripts for the most common tasks:

shell
# play a time-varying mesh sequence
python examples/play_mesh_o4d.py

# play a point-cloud sequence
python examples/play_poincloud_o4d.py

# play a Draco-compressed point-cloud sequence
python examples/play_draco_pointcloud_o4d.py

A typical workflow — convert raw per-frame data into an .o4d sequence, then play it back:

shell
# 1. package raw mesh frames into an .o4d sequence
python open4d/tools/create_o4d_mesh.py

# 2. play it back
python examples/play_mesh_o4d.py

One Python sequence, from open to playback

Keep the existing research examples below as a reference. For the current mesh-sequence API, start with a source checkout and the player extra:

macOS or Linux source setup
git clone https://github.com/open4dfoundation/Open4D.git
cd Open4D
python -m venv .venv
source .venv/bin/activate
python -m pip install -e ".[player]"

Generate a wave locally with no captured data. The homepage recording was rendered from this MIT-licensed generator:

Generated mesh sequence
from open4d.demo import mesh_sequence
from open4d.visualization import visualize

with mesh_sequence(side=24, frames=30, fps=15) as sequence:
    visualize(sequence, up="z")

For your own OBJ or PLY folder, use open_sequence("my_frames/", fps=30) from open4d.io. Numeric filenames determine ordering; a manifest preserves timestamps and metadata. Download the existing ten-frame OBJ/PLY website sample and keep its included MIT license.

Render Gaussian splats

The Qt OpenGL viewer draws projected anisotropic Gaussian splats with opacity, depth ordering, and spherical harmonics through degree three. Playback, synchronized comparison, and the live viewer share the renderer.

A fallback to points is labelled. Neural appearance models keep their own rendering requirements. This generated example tests the viewer without training a model.

Synthetic Gaussian example
from open4d.data import SyntheticGaussianSequence
from open4d.visualization import visualize

with SyntheticGaussianSequence().load() as sequence:
    visualize(sequence)

Compress frames as they arrive

The live sender uses separate compression and transport workers with bounded queues and backpressure. The receiver incrementally decodes framed packets and keeps timestamps and supported attributes.

Raw, zlib, zstd, quantized, and Draco profiles have different geometry support. Live transport does not make an offline neural training process into an online encoder.

See measured throughput
Receiver on the display host
python -m scripts.validate_live receive \
  --host 0.0.0.0 --port 47004 --frames 300 \
  --viewer --report receiver.json
Sender with an existing mesh folder
python -m scripts.validate_live send \
  --host DISPLAY_HOST --port 47004 \
  --source my_frames/ --kind points --profile zlib \
  --frames 300 --report sender.json

The validator converts the mesh to geometry-only points here. For Gaussian frame_*.npz arrays, use --kind gaussians. Unsupported textures are rejected.

Install an actual runtime

Adapters register codecs. Runtimes supply the implementations. The backend manager inspects prerequisites, fetches pinned sources, builds tools in a separate store, and verifies outputs with a native round trip.

Draco builds were verified on macOS and Linux. V-DMC and Faster V-DMC were built and tested on Linux x86_64 with GCC 13. The other nine recipes attach separately installed research environments.

Plan, build, and verify Draco
open4d backend list
open4d backend plan draco
open4d backend install draco --jobs 4
open4d backend doctor draco

Use open4d backend plan vdmc or open4d backend plan faster_vdmc for the Linux build requirements and license details. Installation of those research runtimes requires accepting their listed terms. No runtime redistribution permission is granted by an adapter.

What happens to attributes?

Texture pixels, material indices, and explicit vertex, face, or corner domains belong to the mesh. Each codec declares the fields it can carry; preserving NumPy arrays does not prove native research-codec support.

Verified development profiles
ProfileSupported pathBoundary
NumPy storageExact arrays, attribute domains, owned texturesReference storage
DracoNative generic attributes and UVs, with UV-seam splittingImage pixels use auxiliary storage
V-DMC / Faster V-DMCNative UV and texture coding, verified after a clean buildOpt-in texture profile, one RGB material, lossy remeshing and reparameterization
Other research codecsGeometry or codec-specific appearanceNo general UV or texture guarantee

The .o4d Data Model

Open4D treats time as a first-class signal. Instead of a directory of unrelated per-frame files, an .o4d sequence is a single logical object: an ordered set of geometry frames plus timing metadata, so downstream code — codecs, metrics, players — can reason about temporal structure directly.

Supported content types in the current core:

ContentReader / WriterPlayerCreation tool
Time-varying mesh open4d/io/o4d_mesh_io.py open4d/player/mesh.py create_o4d_mesh.py
Point-cloud sequence open4d/io/o4d_pointcloud_io.py open4d/player/pointcloud.py create_o4d_pointcloud.py
Draco-compressed point cloud open4d/io/o4d_draco_pointcloud_io.py open4d/player/draco_pointcloud.py create_o4d_draco_pointcloud.py

Design Principles

  • 4D-first — time is a first-class signal, not an afterthought
  • Separation of concerns — core abstractions vs. research modules
  • Reproducibility — benchmarks are explicit and scriptable
  • Systems-aware — metrics include bitrate, latency, and temporal stability
  • Cross-domain — XR, robotics, and autonomy share the same foundations

IO — Readers & Writers

The open4d.io package provides a unified interface for reading and writing 4D sequences. Each content type has a dedicated IO module with a symmetric read/write API, so codecs and players are decoupled from on-disk formats.

python — illustrative
from open4d import io

# read a time-varying mesh sequence
seq = io.o4d_mesh_io.read("longdress.o4d")

# iterate frames over time
for frame in seq:
    process(frame)
⚠️

Snippets marked illustrative show the intended API shape. Check the module source and examples/ for the exact, current signatures.

Player

open4d.player renders sequences interactively. It supports mesh sequences, raw point-cloud sequences, and Draco-compressed point-cloud streams — decode happens frame-by-frame, matching how a streaming client would consume the data.

Conversion Tools

open4d.tools packages raw per-frame assets (e.g., a folder of PLY/OBJ frames) into .o4d sequences, including Draco-compressed variants for bandwidth-constrained playback.

Metrics

open4d.metrics hosts quality and temporal metrics used across benchmarks. The design goal is systems-aware evaluation: not just geometric distortion, but the quantities that decide whether a pipeline is deployable —

  • Geometric quality — point-to-point / point-to-plane distortion, mesh distance
  • Rate — bitrate and compression ratio
  • Latency — encode/decode time budgets for real-time pipelines
  • Temporal stability — consistency of geometry across frames, beyond per-frame error

Docker Environments

The docker/ directory provides containerized environments so that experiments run the same way on any machine — a prerequisite for reproducible benchmarks.

FAQ

How is Open4D different from Open3D?

Open3D focuses on static 3D data processing. Open4D targets the time-varying case: sequences of meshes and point clouds whose geometry (and even connectivity) changes every frame, with compression, streaming, and temporal metrics as core concerns rather than extensions.

Can I use only the codecs?

Yes. N4MC, TSMC, and TVMC live in their own repositories/submodules and can be used standalone; Open4D adds the shared IO, metrics, and benchmark scaffolding around them.

How do I contribute?

New modules, benchmarks, datasets, metrics, and documentation are all welcome — see Contributing.
